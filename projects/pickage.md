# Pickage

## 한 줄 소개

- npm 패키지를 입력하면 순수 의미 검색과 구조적 자격 관문(보완재·노후·실체 미달·아카이브 제외)을 통과한 비교 후보를 찾아주고, 사용자가 선택한 최대 3개 패키지의 직접 Dependency 추이·Downloads·최신 버전 분포(Version Share)를 한 보고서로 제공하는 패키지 분석 서비스. SSAFY 15기 빅데이터 분산 트랙 공통 프로젝트로, **2026-09-15 기준 아직 개발 진행 중**이며 완료·수상 사실은 없다.

> 이 문서는 개발이 끝나기 전에 미리 남기는 중간 기록이다. SSAFY 규정상 완료 후에도 소스코드는 공개할 수 없어([`깃든`](gitden.md)과 같은 제약), 코드 원문 대신 문제 정의·범위·의사결정 근거를 서술로 남긴다. 다만 깃든과 달리 프로젝트가 끝나지 않았으므로, "실제 코드로 확인한 사실"과 "기획 문서에 그렇게 적혀 있다는 사실"을 문장에서 구분해서 쓴다. 오늘(2026-09-15) 확인 가능했던 핵심만 우선 채웠고, 나머지는 [다음 갱신 때 채울 것](#다음-갱신-때-채울-것)에 남겼다.

## 문제 정의

패키지를 새로 도입하거나 기존 패키지 교체를 검토하는 개발자는 관련 후보·다운로드·의존 관계·버전 분포를 서로 다른 곳에서 확인해야 하고, 검색 결과가 이름·설명만 비슷하다고 실제로 비교할 가치가 있다는 보장도 없다. 반대로 다운로드 수 같은 인기 지표 하나로 후보를 고르면 목적이 다른 대형 패키지가 섞인다. `Pickage_서비스_기획서_0915.md`는 이 문제를 후보 탐색 분산·의미 유사도만으로 고른 부적격 후보·인기 지표의 관련성 압도·시계열과 스냅샷의 혼동 등으로 구체화하고, `후보 발견 → 비교 대상 확정 → 직접 의존 관계·Downloads 확인 → 최신 Version Share 스냅샷 확인`을 하나의 사용자 여정으로 묶는 것을 MVP 목표로 삼는다.

서비스가 의도적으로 하지 않는 것도 기획서에 명시돼 있다: 가장 좋은 패키지를 대신 고르는 것, 기술 품질 순위를 매기는 것, 실제 설치·실행량을 추정하는 것, 특정 패키지가 왜 교체됐는지 설명하는 것. "후보 랭킹은 기술 품질 순위가 아니라 비교 후보로서의 현실적인 관련성을 정리하는 내부 기준"이라는 원칙이 기획 전반에서 반복해서 강조된다.

## 서비스 범위

### MVP

- 서비스 소개
- npm 패키지명 자동완성·자유 입력 후 서버 존재 검증
- 순수 의미 검색 + 구조적 자격 관문을 통과한 관련 후보 최대 3개 표시(기본 선택 없음)
- 기준 패키지 포함 최대 3개 비교 대상 확정
- 직접 Dependency Total·major 다중 선택 필터, 로그축
- 조회 구간 첫·마지막 유효 관측 간 직접 Dependency 증감(signed)
- 주간 Downloads(직전 7일 합계, 최대 104주)
- 최신 DB Snapshot 기준 major별 Version Share

### 확장 (MVP 이후)

- 정확한 버전의 기능 비교 — 구조화 데이터 + AI + RAG를 우선 검토하고, 여의치 않으면 AI + RAG로 축소
- Evidence Drawer(판정 근거 확인 패널)
- GitHub 커뮤니티 현황(핵심 이슈·실제 논의 흐름)
- 버전 고착 심화·관측된 교체 흐름(flow map)
- 생태계 결과 + 기능 비교를 묶은 통합 PDF
- 직접 의존 유지·유입·이탈 분석(동일 dependent 식별·계산 기준 검증 후)

**2026-09-15 범위 결정**: 간접·전이 Dependency 분석(구 확장-04)은 코드베이스 전체에서 구현이 0건이고 관련 Jira 에픽도 자식 이슈가 없는 순수 계획 단계였음이 확인되어, "나중에 할 확장"에서 "프로젝트 범위 제외"로 정리됐다(`S15P21A506-358`).

## 개발 현황 (2026-09-15 기준)

아래는 이번 세션에서 실제로 저장소 코드를 열어 직접 확인한 항목만 **코드로 확인됨**으로 표시했다. 표시가 없는 항목은 팀이 직접 작성한 `Pickage_0910_to_0915_기획변경_상세분석.md`의 자체 조사 결과를 인용한 것이며, 이번에 재검증하지 않았다.

- **후보 추천 v1 관문** — 의미 검색(cos 유사도) 뒤 보완재·노후·실체 미달 구조적 관문을 통과한 후보만 남기는 로직이 `ai/similarity/similarity_batch_pipeline.py`에 있고, 저장소 archived 여부를 보는 관문(`repo_archived`)도 같은 파일에 구현돼 있다 — **코드로 확인됨**
- **생태계 보고서(1페이지)** — `frontend/src/routes/report/ecosystem/`에 adapter·badges·toolbar·view·metric-chart·package-card 등 다수 파일로 구성된 실제 구현이 있다 — **코드로 확인됨**
- **GitHub 커뮤니티 백엔드** — `backend/.../domain/community/` 아래 Controller·Service·Orchestrator(`CommunityRefreshOrchestrator`)·Validator·Repository·GitHub 클라이언트·rate limit 처리까지 80여 개 파일로 상당히 구현돼 있다 — **코드로 확인됨**. 다만 프런트엔드 `frontend/src/routes` 전체에서 `community` 관련 코드가 전혀 검색되지 않아, 화면 탭은 아직 없다 — **코드로 확인됨(미구현)**
- **기능 비교(확장) 화면** — `frontend/src/routes/report/features/`에는 파일이 2개뿐이고 그중 하나가 `sample.ts`로, 실제 데이터 연동이 아니라 샘플 데이터를 쓰는 뼈대 수준이다 — **코드로 확인됨**
- **PostgreSQL 게시(similar_package)** — `similar_package` 테이블·인덱스 마이그레이션과 이를 조회하는 `PackageQueryRepository`가 존재한다 — **코드로 확인됨**(다만 "원자적 게시" 로직의 구체적 구현 방식까지는 이번에 확인하지 않음)
- **Redis** — 기획 문서(`Pickage_기능별_개발_구상안_0915.md` §14.2)에는 "app 상태 서비스"로 명시돼 있지만, `backend/src/main` 코드와 로컬 개발용 `compose.yaml` 어디에도 Redis 관련 코드·이미지가 없다 — **코드로 확인됨(기획과 현재 코드의 간극)**. 별도 배포 환경에서만 쓰는 것인지는 확인 필요
- **후보 3개 노출, Downloads 로그축·결측 단절·축적 판정, Version Share 카드별 기준일** — 팀 자체 조사(`S15P21A506-309/304/311`)에 구현 완료로 기록돼 있으나, 이번 세션에서 직접 코드로 재검증하지는 않았다(확인 필요)
